## Запуск проекта

### 1. Настройка переменных окружения

Создайте файл `.env` в корне проекта:

```bash
cp .env.example .env
```

### 2. Сборка приложения

```bash
docker compose build
```

### 3. Запуск приложения

```bash
docker compose up -d
```

## Принятые архитектурные решения

### Структура приложения

Код разделён на три основных слоя:

* `application` содержит use case классы, DTO и интерфейсы;
* `domain` содержит общие доменные типы, например `Ticker`;
* `infrastructure` содержит реализацию репозитория PostgreSQL, клиент Deribit API, конфигурацию Celery и обработчики FastAPI.

### Структура базы данных

База данных состоит из двух таблиц:
* `tickers` хранит поддерживаемые тикеры;
* `price_records` хранит исторические значения цен.

Тикеры вынесены в отдельную таблицу, чтобы не дублировать строковое название валюты в каждой записи о цене. Это также упрощает добавление новых поддерживаемых тикеров.

Ограничение уникальности на поля `(ticker_id, timestamp)` предотвращает создание нескольких записей для одного тикера с одинаковым временем опроса, а также создает индекс для ускорения `SELECT` запросов к базе данных.

Цена хранится в типе `NUMERIC`, а не в типе с плавающей точкой, чтобы избежать потери точности.

Unix timestamp хранится в поле типа `BIGINT`, поскольку приложение использует Unix-время и не нуждается в преобразовании часовых поясов при сохранении данных.

### Опрос api

Celery Beat создаёт задачу опроса один раз в минуту, а отдельный Celery Worker выполняет её. Redis используется в качестве брокера сообщений.

Celery Beat и Celery Worker запускаются в отдельных контейнерах, чтобы планирование задач не зависело от их непосредственного выполнения.

Цены всех поддерживаемых тикеров запрашиваются параллельно с помощью `asyncio.gather()`.

Если запрос цены одного тикера завершается ошибкой, успешно полученные цены остальных тикеров всё равно сохраняются. Это позволяет не терять все результаты из-за временной ошибки при обработке одной валюты.

### Асинхронность

FastAPI, HTTPX и SQLAlchemy используются в асинхронном режиме, поскольку HTTP-запросы и обращения к базе данных являются операциями ввода-вывода.

Celery-задача объявлена как синхронная функция, а асинхронный сценарий опроса запускается внутри неё с помощью `asyncio.run()`.

### Внедрение зависимостей

Dishka используется для внедрения зависимостей в FastAPI, включая сессии базы данных, репозитории и use case-классы.

Celery Worker создаёт зависимости отдельно вручную, поскольку он работает в другом процессе и не участвует в жизненном цикле HTTP-запросов FastAPI.

### Управление транзакциями в репозитории

Репозиторий самостоятельно выполняет `commit()` после операций записи и `rollback()` при возникновении ошибки базы данных.

Для данного небольшого приложения управление транзакциями оставлено внутри репозитория, чтобы не вводить дополнительную абстракцию Unit of Work.

### Пагинация и фильтрация API

Методы получения истории цен поддерживают пагинацию через параметры `limit` и `offset`. Это предотвращает возврат неограниченного количества записей.

Дополнительные параметры Unix timestamp позволяют получать записи только за указанный период времени.

Метод получения последней цены возвращает `404 Not Found`, если для выбранного тикера ещё нет сохранённых записей. Методы получения истории в такой ситуации возвращают пустой список.

## Дальнейшее развитие проекта

### Кэширование запросов

Для уменьшения нагрузки на PostgreSQL можно добавить кэширование часто запрашиваемых данных в Redis. 

В первую очередь целесообразно кэшировать последнюю цену каждого тикера, поскольку этот запрос, вероятнее всего, будет выполняться чаще остальных. Ключ кэша может иметь вид latest_price:{ticker}, а значение должно обновляться после успешного сохранения новых цен в базу данных.

Также можно кэшировать результаты запросов истории цен с учётом параметров тикера, временного диапазона, limit и offset. Для таких записей следует установить небольшой TTL, чтобы избежать хранения устаревших данных и не допустить неограниченного роста количества ключей.

### Отказоустойчивость

Реализовать паттерны retry и cercuit breaker при обращениях к внешнему api, а также rate limiter для защиты собственного api
